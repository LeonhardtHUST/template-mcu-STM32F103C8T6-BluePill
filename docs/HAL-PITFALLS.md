# HAL / CubeMX 陷阱与排查边界

来源是派生工程 `hust-sti-measure-2026` 的故障记录，已对照模板锁定的
`framework-stm32cubef1@1.8.7` 源码审核。模板默认只启用 HSI 与 PC13，未移植频率计、
UART、TIM 或 USB 业务。下文的派生工程实板现象不代表模板已通过 L5。

HAL 源码位于 PlatformIO 包的 `Drivers/STM32F1xx_HAL_Driver/`，重点查
`Src/stm32f1xx_hal_tim.c`、`Src/stm32f1xx_hal_uart.c` 和 `Inc/stm32f1xx_hal_tim.h`。
升级包后须重新核对，不能跨版本套用状态机或寄存器副作用。

## H-1：UART 能发不能收

**现象**：轮询发送/printf 正常，接收中断回调却从未进入。

**根因**：`HAL_UART_Receive_IT()` 配置 UART 接收中断源，不代替 CPU 的 NVIC 配置。
还需要正确的 IRQ handler 调用 `HAL_UART_IRQHandler()`。派生工程的 USART1 缺少这条链路。

**对策**：先在 `.ioc` 中配置 USART 的 NVIC 并重新生成，再检查 MSP 中的优先级与
`HAL_NVIC_EnableIRQ()`、中断文件中的 handler。若生成物确实缺少使能，在相应 USER CODE
块内显式使能，并检查 `HAL_UART_Receive_IT()` 的返回值。错误回调按 HAL 的实际接收状态
处理 ORE/帧/噪声错误；只在接收已结束且状态允许时重新挂接，不要无条件重复启动接收。

**证据**：派生提交 `d741bfa`；本次 CubeMX 6.18.1-RC2 隔离生成也只得到 USART1
`SetPriority`，未得到 `EnableIRQ`。这是该配置下的结果，不能推断所有版本/配置都如此。

## H-2：Base_Start 后 READY 自检失败

**现象**：计数器已经启动，但应用的 `htim.State == HAL_TIM_STATE_READY` 自检失败。

**根因**：当前包的 `HAL_TIM_Base_Start()` 检查 READY 后将句柄整体状态置为 BUSY。
但 `HAL_TIM_IC_Start_DMA()` 检查的是通道及互补通道状态，**不会仅因整体 State 为 BUSY
就返回 HAL_BUSY**。报告将这两个状态机混为一谈，不能照搬。

**对策**：按实际 HAL 生命周期设计自检，分别检查整体状态、通道状态和返回值。
若只需要已配置定时器自由计数，可在明确拥有其生命周期时使用 `__HAL_TIM_ENABLE()`；
它只操作 CEN，不维护 HAL 状态，不是通用的 Start API 替代品。

**证据**：派生提交 `7bfd365`；锁定包上述两个函数的实现。

## H-3：停止捕获 DMA 后共享时基停止

**现象**：停止一次捕获后，依赖同一计数器的时基逻辑不再前进。

**根因**：`HAL_TIM_IC_Stop_DMA()` 关闭捕获通道、DMA 请求并调用
`__HAL_TIM_DISABLE()`。当前宏只在 CCER 中所有 CCxE/CCxNE 均关闭时清除 CEN。
因此“停止 DMA 一定关闭计数器”不成立；仍开启的 PWM 通道通常会阻止这个宏关闭计数器。

**对策**：明确计数器的唯一管理者，在停止路径核对其他使用者并按需恢复计数，
或者使用独立定时器。周期性补写 CEN 是派生工程的恢复策略，不作为模板通用修复，
以免掩盖状态错误或破坏有意停止的计数器。

**证据**：派生提交 `a07288d`；锁定包的 `HAL_TIM_IC_Stop_DMA()` 和 `__HAL_TIM_DISABLE()`。

## H-4：高频输入在 DMA 启动窗口产生捕获覆盖

**现象**：高频采集偶发 CC1OF，而完成的读数正常。

**根因**：当前 `HAL_TIM_IC_Start_DMA()` 先开启捕获通道，再启动 DMA，最后开启 TIM DMA
请求。计数器已运行且外部输入持续时，这个窗口可能产生尚未服务的捕获。
窗口时长依赖硬件、编译选项和执行路径，不能普遍写成“十几微秒”。

**对策**：优先在采集协议中控制输入/触发和启动顺序；定位时记录 SR、DMA 剩余长度和错误状态。
派生工程在启动后清 CC1IF/CC1OF，只能作为允许丢弃启动阶段事件的特定策略。
DMA 此时可能已经搬运数据，不能保证首个 CCR 值“不进入缓冲区”，也不能保证仅用相邻时间戳
之差就一定安全。清标志可能掩盖真实覆盖；需要检查样本连续性并做高频实板验证。

**证据**：派生提交 `cf37dff` 的寄存器快照与实板频点记录；锁定包的启动顺序。
本模板未复现其时序或采用清标志补丁。

## H-5：错误发生后没有串口诊断

**现象**：时钟/外设初始化失败后无任何 printf 输出。

**根因**：模板的 `Error_Handler()` 关闭中断并停在无限循环；故障可能发生在 UART
初始化之前。关中断后的中断/DMA 日志也无法正常工作。

**对策**：保留模板默认的停机行为。需要容错的派生工程应单独设计并验证降级启动路径、
安全输出状态和实际时钟，选择此阶段可用的诊断通道。不要简单将 Error_Handler 改成返回；
调用方通常假定它不返回，继续执行可能使用尚未配置成功的时钟或外设。
读取 PCLK 也不能证明振荡源正常、SystemCoreClock 已更新或新波特率必然正确。

**证据**：模板 `Core/Src/main.c` 的错误路径；派生提交 `304049b` 仅证明其专用降级方案。

## H-6：新增外设没有落入生成物

**现象**：`.ioc` 文本看似完整，加载/生成返回成功，实际没有新增初始化函数。

**根因**：可能是信号名、IP/Pin 清单、参数白名单或模式表达式不完整；
派生工程曾遇到 TIM4 被丢弃且没有 `Cannot map`。具体原因没有充分定位，
不能据此认定 CubeMX 不支持 TIM4 或必须复用已有外设。

**对策**：依次核对加载后写回的 `.ioc`、生成日志、`MX_xxx_Init()` 的定义和调用、
HAL 模块开关、MSP 时钟/GPIO/DMA 与 IRQ handler/NVIC；失败时用 GUI 配置并比对差异。
“日志无错误”只是条件之一，不能替代生成物核验。

**证据**：派生提交 `e89cea3`；模板约束见 [AGENTS.md](../AGENTS.md) §2.3。

## 配置能力边界

- 手加参数要同步加入 `<IP>.IPParameters`。引脚/模式也须成套，详见
  [占位符清单](../TEMPLATE-PLACEHOLDERS.md) D3–D5。
- TIM 通道分频在历史 headless 配方中曾被重建成 DIV1，这是特定配置路径的观察，
  不是“所有 `.ioc` 都无法配置 TIM 通道参数”。先检查本机数据库与 GUI 保存结果；
  必须用代码补充时放在 `USER CODE BEGIN TIMx_Init 2` 内，复核生成后仍存在且时机正确。
- USB CDC 配置与分频核验见 [CubeMX 工具说明](TOOLING-cubemx.md) §3.5.6。

本文验证等级为 L1（源码与证据核对）；隔离生成的告警与边界见上述工具说明。
未声称模板已经复现派生工程的 L5 结果。
